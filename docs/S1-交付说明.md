## 1. 一句话

**原来的问题是「跑一次查重就把向量库的字段抹空」，现在从结构上不可能再发生**：写简历向量只剩一个入口，读字段一律回 MySQL。

---

## 2. 改了什么

### 2.1 写入侧：唯一构造入口

| 文件 | 改动 |
|---|---|
| `app/services/vector_service.py` | `_resume_row` → **`resume_row`**（公开，含 `major`），注释写明"upsert 是整行替换，必须走这里" |
| 同上 | `index_resumes()` 调 `resume_row` |
| 同上 | `find_duplicates()` **删掉裸 upsert**，改调 `ensure_indexed()` |

全局搜索验证：`resume_vectors` 的 `store.upsert` 只剩 **1 处**（`vector_service.py:94`），payload 100% 来自 `resume_row`。

### 2.2 幂等索引

| 新增 | 作用 |
|---|---|
| `expected_resume_count(db)` | 库里应被索引的份数 |
| `is_stale(db)` | 行数 ≠ 应索引数 → 过期 |
| `ensure_indexed(db)` | 过期才重建，否则跳过；查重/召回统一调它 |
| `POST /api/vector/reindex-if-stale` | 幂等重建接口 |
| `status(db)` 加 `stale` / `expected_count` | 前端能看出向量库是否过期 |

### 2.3 读取侧：字段一律回 MySQL

| 函数 | 改动 |
|---|---|
| 新增 `load_resume_facts(db, ids)` | 一次 `IN` 查询批量取 `name/education/major/years/skills/filename/created_at`，避免 N+1 |
| `semantic_search_resumes()` | Milvus 只给 `id + score`，字段全从 `load_resume_facts` 取 |
| `find_duplicates()` | 同上 |
| `job_semantic_candidates()` | 同上 |

**新增返回字段**（三处统一）：`major`（专业）、`skills_top`（前 5 项）、`skills_count`（总数）、`filename`（文件名）、`created_at`。

原来 22 项技能串成一坨（`Kubernetes、LangChain、PyTorch…`），现在拆成 `skills_top` 数组 + `skills_count` 数字，前端好排版。

### 2.4 顺带修掉的一个坑

`MilvusStore.count()` 原来用 `get_collection_stats`，它返回的 `row_count` **包含 upsert 产生的墓碑行**——实测 6 行报 18。这会让"过期判据"永远成立，导致每次调用都全量重建。

改成 `query(filter="id >= 0", output_fields=["count(*)"])` 精确计数。注意：`count(*)` **不能带 limit**，否则 Milvus 报 `1100 count entities with pagination is not allowed`。

## 7. 已知边界

1. **向量库仍是「全量重建」粒度**：`ensure_indexed` 只判行数，不判内容。如果某份简历内容改了但份数没变，不会自动重建——需要显式调 `POST /vector/index`。S3 会把"只扫现行简历"接进来，届时行数判据会跟着变。
2. **`count(*)` 依赖 Milvus 支持聚合查询**：standalone 2.4+ 支持；若换成极老版本会回退到 `get_collection_stats`（不精确，但不会崩）。
3. **OCR 仍 3/6**：视觉模型 502 是网关侧问题，本阶段未处理（TODO 0.6 待你点头）。
