# AI 数字化人才平台业务需求说明书

**版本：** V1.0 业务评审稿　　**日期：** 2026 年 11 月 25 日  
**适用读者：** 项目负责人、招聘 HR、培训负责人、业务负责人及系统管理员

## 1. 项目背景与建设目标

### 1.1 项目背景

企业在招聘和培养中需要回答四个问题：**这个人是谁、为什么适合这个岗位、还缺哪些能力、后续是否有证据表明能力得到补足。** 现有项目围绕这四个问题建设了一套内部人才工作台：HR 从简历原件建立档案，按岗位要求筛选并查看理由，组织测评、形成能力画像，再根据岗位差距安排培养；候选人经业务确认后转为员工，员工可查看自己的培养任务和成长记录。

这个平台的价值不只是少录几次数据。它需要让招聘和培训人员在交接时认定的是同一个人，看到的是同一份已确认的证据，并能解释当时为什么作出某个判断。当前项目已有各环节的操作入口，但“能从一个环节进入下一个环节”不等于“有完整的招聘审批、可靠的证据归属和可追溯的历史”。下一阶段应先修正影响人选判断的口径，再补齐人工复核与历史记录，不宜先扩大功能范围。

### 1.2 业务痛点与期望变化

| 业务场景 | 使用者遇到的问题 | 期望变化 |
|---|---|---|
| 收集与整理简历 | 文件格式不一；人工摘录浪费时间；提取结果不准时，容易把缺失当成事实 | 批量收件、清楚反馈每份状态；以原件辅助校对，无法确认的字段明确标记 |
| 重复投递与简历更新 | 一人多份简历可能重复计数；同名者又可能被误认成一人；旧测评容易失去关联 | 区分候选人身份、简历版本和疑似重复；新版本不能吞掉旧证据，也不能串到别人名下 |
| 岗位筛选 | 部门各用一套口径；条件写了不一定生效；一个总分不能说明为何通过或未通过 | 明确硬条件、加分项及证据来源；区分不满足和待核验；招聘人员能据此复核 |
| 找人及补充储备 | 技能和经历写法不同，关键词会漏人；看到岗位缺口，却不知道先复核谁 | 用语义检索和储备推荐补充线索，说明相似点或缺项，但不替代正式筛选 |
| 测评与画像 | 测评结果没有可靠归到本人，或汇成画像后看不出结论依据 | 明确成绩对应的人、卷和作答记录；画像说明各维证据与不足 |
| 招聘转培养 | 建好的员工账号未必关联正确档案；培训选课、学习过程和能力变化互相脱节 | 转员工时明确身份交接；按岗位差距给出培养任务；区分学完、考过和能力更新 |
| 交接、复盘与管理 | 重跑后查看不到上一轮名单；即便有操作日志，也未必知道谁为什么改变业务结论 | 保存每轮筛选的依据、名单和人工决定；同一指标的汇总、名单与可见范围一致 |

以上痛点由现行项目和工作区资料归纳，不代表已完成组织访谈，也不代表已测得节约工时或招聘成效。

### 1.3 建设目标

1. **提高处理效率：** 减少逐份录入、重复查找、跨表核对；批量任务失败后，HR 知道哪些材料需要补查或重办。
2. **让用人判断有据可查：** 对每个岗位和候选人，能解释条件、证据、分数以及人工决定；信息不足时不假装已经确认。
3. **把招聘证据交接给培养：** 简历换版、测评提交和转员工后，仍能在授权范围内识别同一人，保留其有效记录。
4. **保护人才资料：** 让人员只看、只办职责内的事项；访问入口、汇总和原件不能绕开同一可见范围。

## 2. 产品范围与角色

### 2.1 当前范围

| 范围 | 当前承载的业务 |
|---|---|
| 内部招聘 | 工作台、简历上传及校对、版本管理、岗位条件与试算、正式匹配、语义找人、空缺预警和储备推荐 |
| 人才评价 | 候选人和员工两类题库与试卷、绑定和测评结果、错题与复习建议、五维画像和分析 |
| 员工培养 | 候选人转员工建号、课程管理、能力差距诊断、培养计划、本人学习进度、课后考核和成长台账 |
| 基础治理 | 登录、按角色进入、数据范围控制，以及用户、角色与操作记录查询 |

**不计入当前交付：** 外部候选人账号和自助投递、候选人独立考试门户、员工独立自助考试、招聘渠道投放、多轮面试排期、Offer、正式录用审批、完整入离职管理，以及历史方案中的知识库问答、智能问数、智能体编排等。历史方案或菜单出现某个名称，不等于当前可以办理该业务。

### 2.2 人员与责任

| 角色 | 主要任务 | 业务边界 |
|---|---|---|
| 招聘 HR | 收集与校对简历、配置岗位条件、试算和筛选、组织候选人测评、核对候选人后发起转员工 | 可见范围按授权确定，不能因为能进入一个模块就查看其他部门所有人；规则通过不等于录用 |
| 培训管理人员 | 维护课程与计划，对接课后考核，跟踪学习与能力变化 | 当前通常由有相应权限的 HR 或管理员承担；是否单设培训角色、能否代办、跨部门范围须明确 |
| 普通员工 | 查看本人计划、待办、学习进度与成长记录，办理授权的本人学习任务 | 默认以本人培训为主；不应查看招聘名单、他人答卷或学习记录；不等于已具备员工独立考试端 |
| 系统管理员 | 查询用户、角色和操作记录，排查系统管理事项 | 系统管理权限不等于招聘审批权；现行管理主要是查询，并非完整组织、人事和角色管理 |
| 候选人 | 在招聘、测评和转员工流程中作为被服务对象 | 当前不是独立登录角色；有权限的组织者经系统入口办理测评，不能假定候选人可自助操作 |
| 业务负责人 | 提出人数和能力要求，参与复核或评价人选 | 现有资料有业务负责人角色，但其可见范围、复核权和最终决策责任需另行确认，不作为本稿的已验证能力 |

## 3. 核心业务流程与状态口径

### 3.1 四条业务流程

1. **简历入库：** HR 批量上传 → 查看待处理、处理中和结果 → 对失败或待识别的材料补件或重办 → 对照原件校对 → 确认现行简历；疑似重复交人工判断。
2. **岗位筛选：** 维护岗位要求与目标人数 → 试算观察通过人数和分数分布 → 运行正式匹配 → 查阅理由与人选 → 对证据不足者人工核验；可使用语义搜索和储备推荐补人。**保留正式批次、记录复核结论属于拟补需求。**
3. **人才测评：** 按用途维护题库 → 组卷 → 将试卷与简历绑定 → 由有权限人员经工作台组织作答与提交 → 查询成绩、错题和复习建议 → 归属明确的证据供画像使用。
4. **转员工与培养：** 经组织在平台外或约定流程中确认后，授权 HR 发起建号并关联档案；HR 基于岗位能力差距生成计划，员工查看本人任务并学习；符合条件的考核通过后回写能力变化并记录来源。

目前以上环节**不是由同一招聘申请强制串行控制**。例如，简历详情有转员工入口，不代表当前存在面试结果、录用审批或 Offer 校验；培养方案可先于员工建号准备，员工自助查看以正确完成身份关联为前提。

### 3.2 容易混淆的状态

| 对象 | 业务口径 |
|---|---|
| 简历处理 | 等待、处理中、解析完成、失败或待识别。解析完成表示已有可读结果，不等于关键信息已经人工确认。 |
| 简历版本与重复 | 现行版本默认参加业务处理；被替代版本供追溯。语义相似、疑似重复、已确认同一人是三件事。 |
| 岗位结论 | 当前规则结果是通过／未通过。拟补“证据待核验”及独立的人工决定；试算、规则分、语义相似度、人工入围、实际录用互不替代。 |
| 测评 | 简历上区分未测评、待测评、已测评；绑定可以取消。已提交表示有答卷，不等于及格；取消也不等于删除已有成绩。 |
| 培养 | 待学习、学习中、完成、考核未通过分别有不同含义；旧计划作废不应抹掉已发生的学习和考核事实。 |

## 4. 分模块需求

本章的“现行”表示在当前工作区找到对应功能或规则，不等于所有角色、真实数据与异常场景均已验收；“要求”包括应保留的行为与拟完善的目标，后者以第 6 节优先级为准。

### 4.1 工作台与业务概览 REQ-01

**使用者与痛点：** HR 和获授权的管理人员需要先看待处理事项，而不是分别进入各模块查数量；如果总数、队列和名单的计算范围不同，主管拿到的数字不能用于分工。

**现行：** 能查看简历总数、解析情况、待处理队列、在招岗位、匹配概况和近期操作。现行部分汇总与明细的可见范围仍须专项确认；“最近匹配”也不能当作完整的历史运行清单。

**要求：** 指标标明计算对象、时间范围和可见范围。例如“全公司在招岗位”与“我可见岗位”不能混称；当指标可下钻时，得到相同口径的列表。无数据、未运行过、读取失败和无查看权限应区分；对 HR 给出能继续办理的入口。

**验收示例：** 向某部门增加一个待处理事项，该部门 HR 的概览与相同筛选条件下的列表一致；另一个无权限部门不会看到该事项或其个人明细。

### 4.2 简历接收 解析与人工校对 REQ-02

**使用者与痛点：** 招聘 HR 集中处理多种来源的简历，需要知道每份是否成功、哪部分读不出来，以及自动填出的姓名、学历、技能、专业和年限该信到什么程度。

**现行：** 支持批量上传并按需注明岗位，保留原件和处理结果；可筛选、查详情、校对并按权限下载。文本版 PDF、DOCX、TXT 等可提取；图片和扫描件的结果取决于识别能力，旧版 DOC 不承诺直接解析。校对不会自动替换已有正式匹配结论。

**要求：** 批量部分失败时保留成功项，逐份显示失败原因和后续动作；无可用正文的材料不得当作成功。对未提取或证据不清的关键字段保留缺失状态；校对保留原件，能区分提取值和已确认值。进入筛选的应是已完成处理、处于现行版本且操作者可见的简历；已有结果若引用旧证据，应能识别，不能悄然改写。

**验收示例：** 一次提交一份有效文件和一份超限文件，前者可单独继续，后者说明问题；扫描件无法识别时不会出现推测的学历或年限；补正年限后可与原件核对，原有匹配不会无提示变分。

### 4.3 身份识别 查重与版本管理 REQ-03

**使用者与痛点：** HR 必须能区分“同一人更新了简历”和“两个经历相似的人”，否则会重复统计、误改联系方式，甚至串联测评和员工档案。

**现行：** 以整理后的手机号优先、邮箱补充判断，形成现行与历史版本；满足部分同名、同学历、同专业条件时可提示疑似重复。现行简历换版后已有部分关联承接，但不同身份线索冲突、个别关联未承接等场景仍需核对。

**要求：** 人员身份与某一份简历分开确认。对手机号共享、换号、手机号与邮箱指向不同对象等情况，不只凭一个字段自动合并；交人工复核并保留判断理由。换版后能追溯原件，确认测评、画像、计划、台账和员工账号仍归原人；对无法确认的关联保留待查，不默默丢弃或迁给他人。统计若用“人数”，应按人员而不是文件份数计数。

**验收示例：** 一人两份已确认简历只以现行版本参加新筛选，仍能找到旧版及其有效测评；两个同名者的手机号或其他证据冲突时，系统提示复核，不自动合并。

### 4.4 岗位条件与条件试算 REQ-04

**使用者与痛点：** HR 和岗位负责人要把岗位描述变成一致的筛选标准，且能在正式筛选前看清条件是否过严；能填写而不能真正判定的条件会误导用人。

**现行：** 可维护岗位条件、人数、合格线、分项权重和能力基线，也可从岗位说明生成可编辑建议。可对可见简历试算分数、通过人数和分布，不改正式名单。专业等字段能配置，但目前并非每项已保存条件都会按预期判定。

**要求：** 区分必须满足、优先加分和仅供参考的项目。逐项约定比较方式、证据来源、缺失时的处理、等于门槛时的判断；无法按约定执行的条件不得作为正式硬条件发布。从岗位说明生成的建议必须经授权人员确认。试算明确所用规则和样本范围；规则和样本相同时，与正式匹配的判断一致。

**验收示例：** 岗位规定某专业为必须条件时，不符合者不能因高分通过；无法核实专业时进入待核验。更改条件后试算可以变化，但旧正式名单不因试算改变。

### 4.5 正式匹配 结果解释与人工复核 REQ-05

**使用者与痛点：** 招聘 HR 不只要名单，还要知道每个人为何通过或未通过，并在用人争议或交接时还原当时使用的简历和规则。

**现行：** 按岗位规则计算并保存当前结果，展示合格线、硬条件、分项、理由和简历入口；岗位设有能力基线且人有画像时，画像可参与。再次正式运行会重建该岗位当前结果；未形成独立的历次结果和 HR 决定历史。合成样例中，岗位要求的专业不符，但仅补联系方式就从 **67 分未通过变为 70 分通过**，说明现行配置生效和评分口径都需要修正。

**要求：** 问题按“证据明确不满足”“证据不足需核验”“确认满足”分别处理；联系方式、档案填报是否完整不计入岗位能力评价。结果必须解释每条硬条件、分项得分及其来源。拟为每次正式匹配保留范围、时间、岗位规则、使用的简历及能力证据和当时结果；之后重跑或简历更新不得改写旧批次。授权 HR 另记入围、暂缓或不通过，写清操作者、时间与理由；人工改判不覆盖原规则结果。

**验收示例：** 只补手机号和邮箱不能改变能力分；明确未满足硬条件不能因高综合分通过；更新简历和岗位要求后，旧批次仍可查；人工入围和系统结果可同时核对。

### 4.6 语义检索 相似简历与岗位召回 REQ-06

**使用者与痛点：** 同类岗位经验和技能有不同说法，关键词会漏掉合适的人；表达相似也可能只是简历写法相近。

**现行：** 可用自然语言找简历、辅助发现相似简历、按岗位找相关人选，并展示摘要与相似度。相关能力不可用或资料更新未及时反映时，结果可能缺失或滞后。

**要求：** 用于发现人选和核查线索，不作为硬条件、正式排名或身份合并依据。结果说明相关点，使用可访问的当前业务资料；无权限的人不能通过摘要、列表或点击详情间接读到。不可用与“有效搜索后没有结果”应区分，并保留普通条件搜索和岗位匹配。

**验收示例：** 相近经历的不同表述可作为测试样例；高相似度但缺必需技能的人可被发现，不能自动列为正式通过；搜索不可用时仍能按条件筛选简历。

### 4.7 空缺预警与储备推荐 REQ-07

**使用者与痛点：** 部门希望尽早知道当前候选池是否够用，以及还可以复核谁；不能把筛选合格人数误报为已经入职的人数。

**现行：** 按岗位显示需求人数、已匹配人数、通过人数和预警；储备候选人可以来自接近合格线或符合画像条件的人选。目前缺口按“需求人数减当前匹配通过人数”计算，最低为零，是筛选供给指标，不是真实在岗空缺。

**要求：** 明确提示统计基于哪一次结果、哪个范围和哪类人；区分尚未匹配、匹配后无人通过、人数达到需求三种状态。储备项说明差距、推荐依据及需补查的硬条件；储备不占已合格或录用名额。若未来需要真实在岗空缺，应另行定义已录用、已到岗和人员退出的统计来源。

**验收示例：** 某岗位需 3 人、当前 2 人通过，显示筛选缺口 1 人；新增一名储备人选不改变缺口；某岗位尚未执行匹配时提示“尚未匹配”，而不能把它解释为已经筛过但无人通过。

### 4.8 题库 试卷与智能测评 REQ-08

**使用者与痛点：** 测评组织者需要复用题库，又要防止试卷用错人群、答卷绑错人、题目导入错误或成绩缺少可查依据。

**现行：** 题库和试卷分候选人、员工两类；支持单选、多选、填空与简答。可逐题录入或批量导入，经预览、编辑和确认后入库，重复题干会跳过。可按知识分类组卷，给一份或多份简历绑定试卷；提交后出成绩、分题结果、错题和复习建议。客观题按评分规则处理，简答可在条件允许时使用 AI 辅助评分。受众、截止、重复提交和人员归属的各类边界尚不能视作全部落实，当前没有独立考生端。

**要求：** 导入预览与正式入库分开，展示合法、重复、失败数量及原因；取消预览不新增题目。测评明确人员、试卷、用途、受众、实际提交时间和成绩，历史能回查当时试卷和评分依据。取消绑定不得删除有效历史成绩；过期、重复、误绑和补考分别定义处理规则。对主观题保留评分理由及人工复核入口；组织者的操作记录不能替代实际作答人身份。

**验收示例：** 同名两人分别绑定试卷，提交后各自查看的是本人的答卷和成绩；用错试卷或受众时不接受；导入取消后题库数量不变；重复提交不得制造第二份有效成绩，补考须是独立、明确授权的一次安排。

### 4.9 人才画像 能力报告与证据 REQ-09

**使用者与痛点：** 招聘和培养人员需要了解能力结构，而非只看综合分；如果画像把同名者成绩算进去，之后的匹配与培训都会受影响。

**现行：** 使用简历中的学历、技能、经历及可用的测评证据，形成技术深度、工程能力、业务理解、协作沟通、成长性五维画像，展示标签、等级、优势、短板与可用的变化记录，供岗位匹配和培养参考。当前画像的部分测评证据按姓名归集；课后考核也有类似的身份判断问题。

**要求：** 画像说明每一维来自哪些有效证据、何时产生、是否已经确认；没有证据的维度标“证据不足”，不等于能力低。旧成绩无明确归属时单列待查，不自动参加画像或匹配。区分简历自述、测评成绩、有效课后考核和 AI 生成的概述；概述不作为新事实。更新画像能解释变化来源，不因重复提交同一证据重复增加能力值。

**验收示例：** 同名两人各有一份成绩，各画像只计入各自有效证据；更换简历版本后，已确认的本人测评仍可追溯；没有有效考核的人不出现凭空生成的成绩。

### 4.10 候选人转员工 REQ-10

**使用者与痛点：** 候选人成为员工后需要进入本人培养空间；重复建号、占用手机号或给错人会导致培训记录和人才资料错配。

**现行：** 从简历详情由授权人员发起建号，以手机号作为登录账号并分配员工角色，关联简历及已有画像；对缺少必要手机号、重复转入和账号占用有拦截。初始凭据在创建时提供，正式使用前仍需确定发放和改密流程。这一步不是录用审批。

**要求：** 建号前确认人员、手机号、部门和操作权限，明确转入的业务依据；账号冲突转人工核对，不能覆盖他人账号。建号成功后只开放员工本人获授权的培养内容；失败时明确是否创建成功以及下一步责任人。初始凭据不得出现在可被他人查询的记录里；约定交付、首次改密、重置及离职停用责任。

**验收示例：** 同一人反复发起不产生多个员工账号；账号被其他人使用时阻止办理。正确转入的员工可查看本人已有计划，无计划时看到明确提示；不能进入招聘名单或他人计划。

### 4.11 课程维护 差距诊断与培养计划 REQ-11

**使用者与痛点：** 培训人员需要把“画像得分不够”变成可以执行的学习任务，而不是发一份通用题单；课程不匹配或目标不明确时，员工不知道学来做什么。

**现行：** 可维护课程，按岗位基线比对人员画像，展示现值、目标和差距，形成阶段计划与学习任务；计划可包含周期、导师与相关课程。针对同一人和岗位重新生成时，现行会作废旧计划。部分维度没有合适课程时，不能视为已经完成资源配置。

**要求：** 培养计划明确适用岗位、目标维度、优先级、负责人、周期、课程与完成标准。区分岗位明确给出的目标和通用参考目标；差距不足以确认时要求先补证据。无适配课程提示资源缺口并支持人工安排。替换已有计划前说明对待办、已完成任务和考核的影响，保留旧计划与真实学习记录；已被使用的课程变更不应抹掉当时的安排。

**验收示例：** 某维现值 50、目标 70，能够看清 20 分差距、相应课程或待配置项；重新生成计划后只显示有效计划为当前待办，但旧计划及已发生的学习事实仍可追溯。

### 4.12 员工学习 课后考核与成长台账 REQ-12

**使用者与痛点：** 员工需要知道还有哪些任务、如何完成；HR 需要区分“记录了学习时间”“课程已完成”“考核通过”和“能力有证据变化”。

**现行：** 员工可查看本人计划、进度、待办和台账，并在授权范围内记录学习进度。手动完成要求进度达 100% 且学时达标；目前记录的进度和时长不能视为独立证明。可关联测评作为课后考核；在满足条件时，考核通过可更新对应画像并记入台账，未通过可进入复习。考核的本人及课程归属还需加强，员工独立答题不在当前范围。

**要求：** 任务告知进度、累计学时、是否必考和完成条件。要求考核的课程不能仅靠手动标记为最终通过。接受成绩前核对是否为本人、是否为指定试卷或等效考核、是否适用该次计划；不能仅凭姓名。台账记录变化前后、依据、时间和办理人，对无能力变化的通过结果保留考核事实但不虚增能力分。同一证据不得被反复计算；历史错记有正式纠正记录。

**验收示例：** 进度或学时不足不能手动完成；他人答卷、不同课程答卷不能完成本任务；重复使用同一有效考核不重复记账；两个员工不能看到或修改对方任务。

### 4.13 登录 权限 系统管理与操作记录 REQ-13

**使用者与痛点：** 员工、HR 和管理员通过同一平台工作，承担的任务和可见资料却不同；仅隐藏入口不足以证明资料不会被看到。

**现行：** 可登录、退出并按角色进入授权范围；系统管理主要提供用户、角色和操作记录查询。通用操作记录能辅助排查，不等同于人员身份合并、人工筛选、成绩改判等业务决定的追溯。

**要求：** 明确谁能看、谁能办、可以办哪些对象，覆盖列表、搜索摘要、统计、详情、原件、答卷、画像、计划及台账。授权、身份合并、人员转入、人工决定、考核纠正等关键动作，应记录操作者、时间、对象、理由和结果。敏感字段仅在职责需要时展示；日志与演示资料不包含初始凭据、完整简历或非必要联系方式。演示账号和示例资料不得直接作为正式使用入口；留存、归档、删除及异常处理由业务方指定责任人。

**验收示例：** 设置两个部门和两个员工，分别核对其可见范围；无权者不能从概览、原件或测评旁路得知对象信息；一条人工改判可追溯到人员和岗位，但不会覆盖当时的规则结果或暴露未授权资料。

## 5. 跨模块业务规则

| 编号 | 规则 | 业务说明 |
|---|---|---|
| RULE-01 | 人员身份不等于文件、姓名或登录账号 | 一人可有多份简历、多次测评；同名者可为不同人；手机号既可用于联系或建号，又可能变更，不能被当作唯一的长期身份事实。 |
| RULE-02 | 当前资料和历史事实分开 | 现行简历、画像和计划用于办理当前事项；旧筛选、有效答卷、已经发生的学习和证据应按当时口径追溯。校对或重跑不能悄然改写历史。 |
| RULE-03 | 建议与确认分开 | 简历自动提取、岗位条件建议、语义相似、简答辅助评分和画像概述均有使用边界；正式条件由授权人员确认，录用与人事处理由业务人员负责。 |
| RULE-04 | 决策口径和数据范围统一 | 一项结论应同时说明对象、规则、数据范围和时间。汇总不能比明细知道更多未授权个人信息；岗位合格数不能冒充在岗数。 |
| RULE-05 | 缺失、有冲突和明确不符是三种状态 | 缺失或冲突交待补件、核验或人工处理，不编造信息，也不把“不知道”当作已确认不合格或合格。 |
| RULE-06 | 关键操作不重复产生结果 | 重复上传、提交、转员工、记学时或回写成长不能导致不合理的重复结果；失败后可区分尚未办理、已成功和需人工核查。 |

## 6. 后续完善优先级

以下为建议评审顺序，不代表已经排期或承诺交付。P0 关系到人员判断与资料安全，应先于新功能；P1 让负责人能回看、能分工；P2 再提高日常处理效率。

| 优先级 | 事项 | 完成判据 |
|---|---|---|
| P0 | 修正岗位条件和评分口径（REQ-04、05） | 已发布的硬条件均能正确判定；证据不足进入核验；联系方式不再改变岗位能力分；试算与正式规则一致。 |
| P0 | 修正测评、画像、课后考核的证据归属（REQ-03、08、09、12） | 同名人员不串分，错误试卷和重复有效考核被阻止，无明确归属的旧成绩进入待核查。先处理已确认关联，再分批核对历史冲突。 |
| P0 | 核对对象权限与初始账号交接（REQ-01、06、10、13） | 不同部门和员工只能看到职责内的人员、汇总和原件；确认正式环境不用演示入口或凭据；关键资料和账号的责任人明确。 |
| P1 | 保留岗位规则和正式匹配历史，增加人工复核（REQ-04、05） | 重跑不覆盖旧批次；可查看当时证据和分数；人工决定可查询且与系统判断并列。 |
| P1 | 明确岗位缺口、储备和概览口径（REQ-01、07） | 汇总与明细一致；匹配未执行和匹配无人通过可区分；储备和实际入职不混算。 |
| P1 | 完善培养计划交接与完成标准（REQ-10、11、12） | 当前计划与历史分明；课程、进度、必考、最终完成和能力变化都有可核对依据。 |
| P2 | 提高批量处理、资料更新和异常恢复效率（REQ-02、03、06） | 跨批次、失败后或资料更新后仍能检查每份状态，明确补件与恢复方式；查找能力降级不阻断日常筛选。 |

招聘审批、独立考生端、真实到岗缺口、知识问答等如需推进，应单独确认业务价值、负责人和验收范围，不作为上述整改的前置条件。

## 7. 效果衡量与业务验收

### 7.1 度量指标

首次试用先按固定样本和统一口径建立基线，同时记录样本量、周期、岗位和文件类型。没有基线之前不承诺准确率、节省比例、处理时限或招聘转化率。

| 指标 | 建议口径 | 评审意义 |
|---|---|---|
| 简历处理耗时 | 从文件进入待处理，到关键字段可供筛选的时间；按文件类型和批量规模分别统计 | 判断 HR 等待与校对的负担是否下降 |
| 关键字段人工修正率 | 被人工改正的已复核关键字段数 ÷ 已复核关键字段数；另列漏提取和不确定件 | 区别真实质量提升与少复核导致的表面改善 |
| 硬条件判定正确性 | 经人工标注的“满足／不满足／待核验”样本中，分类正确的条目占比；另看误通过 | 防止通过率好看却把明确不符合者纳入 |
| 筛选决定可追溯率 | 可查到当时规则、简历、证据和人工决定的抽查记录数 ÷ 抽查记录总数 | 衡量复盘时能否还原实际决定 |
| 有效测评归属与冲突数 | 有明确人员和试卷的有效答卷占比，另计同名冲突、误绑、无法确认的旧成绩 | 防止错分进入画像与成长记录 |
| 培养任务完成与考核通过 | 完成任务数 ÷ 纳入本周期的有效任务数；另计应考、实考、通过，区分未考和未通过 | 既追踪学习推进，也避免用完成率代替能力提升 |

### 7.2 关键验收场景

| 场景 | 必须能够说明的结果 |
|---|---|
| 混合简历与多人同名 | 批量部分失败可恢复；一人多份只用现行版本；同名不同人不自动合并；原件和旧证据能追溯。 |
| 试算、正式匹配与复核 | 试算不改正式结果；硬条件、缺失证据、等于门槛可分别验证；重跑与人工决定不破坏旧记录。 |
| 测评与画像 | 题库导入与正式确认分开；错卷、重复和越界场景有明确阻拦；画像只使用归属明确的证据。 |
| 录入员工与培养 | 建号不等于录用；冲突不覆盖他人；本人可继续学习；不满足学时、必考或归属要求不确认完成或成长。 |
| 权限与资料保护 | 不同部门、不同员工按相同口径验证工作台、搜索、名单、详情、原件、画像与台账；允许和拒绝两条路径都要验。 |
| 异常与替代路径 | 扫描件不可识别、语义搜索不可用、缺少课程时，给出明确状态和可执行替代动作，不能当作成功或无业务数据。 |

### 7.3 本次核对范围

本稿以现行工作台、各业务模块行为、现有需求、阶段交付和测试资料交叉核对。对 **32 份合成简历的六个关键字段**及 **36 条基础匹配判定**重跑了工作区已有的离线检查，所覆盖的预期项全部一致；另用合成样例核对了第 4.5 节的专业条件和联系方式问题。样例结果不代表真实简历的解析准确率，也不代表当前流程已通过全量业务验收。本次未连接业务环境执行写入，也未验证真实权限、扫描件识别、独立访问及完整跨模块交接。

## 8. 需要业务方确认的事项

| 待确认问题 | 建议评审人 | 不确认带来的影响 |
|---|---|---|
| 哪些岗位字段是真正的硬条件？缺失、同义表达、等于门槛和特殊例外怎么判？ | 招聘负责人、岗位负责人 | 无法统一试算、正式匹配和人工复核口径 |
| 候选人身份冲突由谁确认？一人跨部门或跨岗位时，哪些档案可共享，哪些只能由原经办人看？ | HR 负责人、资料管理负责人 | 可能发生重复计数、误合并或过度共享 |
| 人工入围、暂缓、不通过和改判分别由谁办理，是否需要双人确认，何时可转员工？ | HR 负责人、业务负责人 | 招聘责任与建号权限易混用，不能定义业务验收边界 |
| 测评的截止、迟交、补考、主观题复核和错绑纠正如何处理？候选人与员工是否需要独立考试入口？ | 测评、培训负责人 | 无法确认哪些成绩可被画像和培养使用 |
| 哪些学习任务必须考核？可接受的学时和能力证据是什么？计划变更时如何承接？ | 培训负责人、导师代表 | 完成率和成长数据可能失真，员工不知道怎样完成任务 |
| 平台只需报告筛选供给缺口，还是还要报告真实到岗缺口？如需后者，谁确认录用、到岗和离岗事实？ | 招聘与业务负责人 | 管理层容易把潜在人选当成已补足人手 |
| 简历、答卷、画像、账号与决策日志保留多久？谁授权查看或提供原件，何时归档或删除？ | 项目负责人、资料管理负责人 | 无法确定资料处理范围和日常治理责任 |

**建议本轮评审先拍板三件事：** 正式岗位条件怎么判、测评如何确认归属、HR 与员工各能看哪些资料。确认这三项后，再评审批次留痕、人工复核与培养变化记录。
