## 1. 产品背景、目标与边界

### 1.1 使用场景与痛点

| 场景 | 当前要解决的业务问题 | 产品价值 |
|---|---|---|
| 集中收简历 | 多种文件格式、信息分散、HR 需要重复摘录字段 | 把逐份抄录变为批量提取和人工校对，保留原件以便核验 |
| 同一岗位多人筛选 | 筛选口径不一致，列表有分数却说不出原因 | 显式配置岗位条件，输出逐项证据、得分和不通过原因 |
| 寻找合适人才 | 精确关键词可能漏掉表达不同但经历相似的人 | 语义搜索、岗位召回和储备推荐提供补充线索，不替代正式规则判定 |
| 重复投递或修改简历 | 一个人多份档案，旧测评或培养关系容易被重复计算或丢失 | 区分现行版本和历史版本，对疑似重复提供人工判断线索 |
| 测评与培养脱节 | 成绩、画像、岗位能力缺口和课程各自独立 | 将可确认的测评和学习结果转为能力证据，连接培养计划和成长台账 |
| 岗位规则或人选变化 | 事后无法说明当时为何入围、暂缓或转为员工 | 下一阶段保留不可被重跑覆盖的决策依据和人工结论 |

### 1.2 产品目标

1. **降低重复处理成本**：HR 能从上传、解析、校对到匹配，在同一套系统内完成工作。
2. **把筛选依据说清楚**：招聘人员能区分硬条件、不完整证据、加权得分、语义相似度和人工决定。
3. **保留可验证的关联**：简历、岗位、测评、画像、培养和员工账号之间能通过明确的标识追溯。
4. **保留人工决策责任**：系统给出证据和建议，HR 决定入围、暂缓或不通过。系统分数、模型建议和实际录用不得等同。

**当前边界：**以内部 HR 作业和员工培训为主。不承诺外部候选人账号或自助投递、独立在线考试门户、多轮面试排期、Offer 发放、完整入离职管理。知识库问答、智能问数、Agent 编排等出现在历史设计或菜单中的内容，不是当前 MVP 已交付功能。

## 2. 用户与权限

| 角色 | 工作目标 | 当前权限与边界 |
|---|---|---|
| HR 管理员 | 处理简历、配置规则、组织测评、生成画像与培养计划 | 核心业务操作者。简历、匹配等按权限和可见数据范围使用；初始化口径下岗位条件可跨部门查看和配置。不能将“HR”理解成所有资源均可读写。 |
| 系统管理员 | 查看用户、角色、操作日志，处理系统级运维 | 支持全局权限。当前系统管理页主要是查询，不等同于完整用户、组织、角色在线管理。 |
| 普通员工 | 查看本人培养计划、任务、学习进度和成长台账 | 默认仅进入培训成长；本人范围内执行已授权学习操作。独立自助测评不在当前版本范围。 |
| 候选人 | 作为招聘、测评和转员工的业务对象 | 目前不是独立登录角色。候选人答题流程由有测评权限的人员经系统页面操作。 |
| 业务负责人 | 关注本部门招聘和岗位缺口 | 有历史角色配置，但不作为当前覆盖和验收主角色；若启用，应另行确定权限与交接流程。 |

**权限规则：**菜单和前端路由用于引导，不能代替服务端鉴权。服务端需同时判断资源、动作、数据范围（全局 / 部门 / 本人）和具体对象归属。列表、详情、查询汇总、导出或附件下载应遵守相同的授权边界；当前不是所有入口都已证明满足该规则，见 NFR-01。

## 3. 核心流程与状态

### 3.1 当前业务流程

```text
HR 上传简历 → 入解析队列 → 提取与结构化 → 校对 / 查看版本 → 进入可匹配简历集合
HR 配置岗位条件 → 试算（不落正式结果）→ 正式匹配 → 查看结论、名单与缺口
HR 从题库出卷 → 绑定简历 → 作答并提交 → 成绩、错题、复习建议 → 画像使用测评证据
HR 从简历详情发起转员工 → 创建员工账号 → 员工登录 → 本人计划、任务与成长台账
HR 诊断候选人能力差距 → 生成培养计划 → 学习 / 课后考核 → 符合条件时更新画像和台账
```

这些能力在产品中可串联，但**当前不靠统一的“岗位申请单”强制串行**：例如转员工入口在简历详情，不代表已有面试、录用审批或 Offer 状态的前置验证。规则匹配中的「通过」等于达到该次筛选标准，不等于实际录用。

### 3.2 主要状态与口径

| 对象 | 当前状态或转换 | 业务解释 |
|---|---|---|
| 简历解析任务 | 等待 → 解析中 → 完成 / 失败 / 需要 OCR | 失败或缺少可用文本不应被当成完成。现行匹配只选已成功解析的现行简历。 |
| 简历版本 | 现行 / 已被替代 | 默认业务列表使用现行版本；有权限的人可查看历史，替代不是物理删除。 |
| 正式匹配 | 通过 / 未通过 | 由当前硬条件和门槛产生；不是录用状态。当前重跑会替换该岗位已有匹配结果。 |
| 测评绑定 | 待提交 → 已提交，或取消；聚合为未测评 / 待测评 / 已测评 | 绑定记录含试卷、简历及关联提交；取消不等于删除已生成的成绩。不能把截止字段或试卷时长配置视作已经具备安全考试控制。 |
| 学习任务 | 待学习 → 学习中 → 完成；考核可能失败 | 手动完成需要进度 100% 且达到学时；考核通过或失败走考核分支；只有满足台账记录条件的考核才写入能力变化。 |

## 4. 功能需求清单

下表的“验收口径”用于组织复测，不代表已全量执行。需要写入测试数据的场景均在隔离环境进行。

### 4.1 工作台、简历与人才库

| ID | 需求 | 状态与现行边界 | 验收口径 |
|---|---|---|---|
| FR-01 | **工作台概览**：查看简历总量、处理状态、待处理队列、匹配概况和近期操作。 | 已实现；部门范围下的汇总与明细一致性还需专项复测。 | 空数据展示正常；导入一份简历前后，队列与相应状态变化可核对；不同部门访问时，不应显示未经授权的明细。 |
| FR-02 | **上传与解析**：批量接收简历，可附关联岗位信息；保留原件、任务、日志和结构化结果。提取姓名、联系方式、学历、专业、年限、技能等。 | 部分实现。单文件上限为 10 MB 级（代码为 10 × 1024² 字节）。文本版 PDF、DOCX、TXT 等走文本处理；图片、扫描件依赖 OCR；旧 `.doc` 不作为有效直解析格式。当前由界面请求推进队列，尚无独立恢复型 worker。 | 有效文件产生任务和结果；空文件、超限和不支持格式给出失败信息；扫描件在视觉能力不可用时不伪造字段或成功状态。 |
| FR-03 | **查看、校对与下载**：按关键字、学历等筛选；详情展示提取字段、原文、解析记录，以及可用的测评摘要；授权用户能够修正结构化字段并下载原件。 | 已实现。修改简历不会自动重算已有正式匹配。 | 可定位一次修改后的字段；原文件仍可核验；无权访问者无法读取详情或下载原件。 |
| FR-04 | **身份去重与版本管理**：手机号优先、有效邮箱兜底形成身份键；同键按版本选择现行简历。同名、同学历、同专业但缺少可靠共同身份键的，仅提示疑似重复。 | 部分实现。已有历史版本与关联迁移，但身份仍依赖简历记录，不是稳定候选人主档；关联迁移失败可能被跳过。 | 同一归一化身份键的两份简历只有一份默认可用于匹配；历史可追溯；相似但不同身份的人不能被自动合并。 |

### 4.2 岗位配置、匹配、语义检索与缺口

| ID | 需求 | 状态与现行边界 | 验收口径 |
|---|---|---|---|
| FR-05 | **岗位条件管理**：维护岗位名称、筛选条件、权重、通过门槛、需求人数和能力基线；支持从 JD 文本生成可人工修改的条件建议。 | 部分实现。配置层可接受专业、城市等字段，但现行硬条件执行不完整；JD 结果是建议，不自动代表业务口径已确认。当前没有规则发布版本。 | 合法配置可保存和回显，非法格式被拒绝；目标态中，每项已发布的字段与运算符都有对应的执行测试；不支持的组合不能被静默忽略。 |
| FR-06 | **试算和正式匹配**：试算查看候选人分布和通过情况，不落正式结果；正式匹配对当前可见且解析完成的现行简历执行规则，保存结论。 | 部分实现。正式运行会在事务内重建岗位结果；批次历史和人工复核状态未实现。 | 同一输入与同一规则得到一致的结果；试算不改正式名单；被替代简历、未解析成功简历不进入正式结果。 |
| FR-07 | **结果解释**：展示得分、门槛、硬条件结果、分项权重和原因，允许从匹配结果进入相关简历。岗位设能力基线且有画像时，可计入画像契合程度。 | 部分实现。默认存在档案完整度分项，手机号与邮箱会影响该项；尚未把证据缺失、条件不满足、待人工核验严格拆开。 | 分项、权重、总分和原因能互相核对；目标态中，仅补联系方式、未新增岗位证据时，不改变岗位能力分。 |
| FR-08 | **语义检索、相似简历与岗位召回**：输入自然语言检索简历，查看相似简历和岗位相关候选人，根据可用索引返回相似度与简历摘要。 | 部分实现。依赖嵌入服务与向量库；业务字段回 MySQL 查询；条数一致不代表内容索引是最新的。语义相似、疑似重复、已认定同一身份是三个不同概念。 | 向量不可用时明确提示，仍可使用文本筛选和规则匹配；任何可点击详情必须有访问权限；相似结果不会改变正式分数或自动合并。 |
| FR-09 | **空缺预警与储备推荐**：按岗位显示名额、匹配人数、通过人数、空缺与预警；展示接近合格线或符合画像条件的储备人选。 | 已实现。现行缺口按“需求人数减匹配通过人数”计算，下限为零，**不是真实入职缺口**；近线储备的现行分差为 15 分。 | 三个名额、两名合格候选人时显示缺口一人；来源、分差与推荐原因可识别；储备不等于入围或录用。 |

### 4.3 测评、画像、转为员工与培训

| ID | 需求 | 状态与现行边界 | 验收口径 |
|---|---|---|---|
| FR-10 | **题库、题目和草稿导入**：题库和试卷标记候选人/员工受众。支持单选、多选、填空和简答；导入 TXT、MD、CSV、DOCX、文本 PDF、XLSX 后预览和编辑，确认才写库，重复题干跳过。 | 已实现。导入上限为单文件 10 MB 级、单次 200 题；文本 PDF 与扫描 PDF 的支持不同。 | 草稿页关闭后题库无新增；确认后写入合法题并反馈跳过项；格式错误及扫描件给可理解的提示。 |
| FR-11 | **出卷、绑定与评分**：从题库组卷，支持按知识分类选题；可单个或批量绑定简历、查看测评摘要；提交计分并产生错题和复习建议。客观题按规则计分，简答题支持规则及可用 AI 复核。 | 部分实现。受众字段和页面筛选已存在，但不等于跨接口都严格校验试卷受众、截止、重复提交和对象归属。候选人和员工独立考生端不在当前范围。 | 一条待提交绑定完成后能回查实际试卷和成绩；不能用错误试卷处理绑定；目标态中，重复提交、截止边界、同名对象与并发均有回归。 |
| FR-12 | **五维画像及报告**：从学历、技能、经历及可用测评证据生成技术深度、工程能力、业务理解、协作沟通、成长性指标；展示优势、短板、等级和能力变化。 | 部分实现。可把测评分项混入画像，并供匹配和培训使用，但当前按姓名归集测评，有同名串分风险；AI 主要用于摘要或分析表达，不作为事实来源。 | 同一输入可解释得分来源；目标态中，同名不同人的成绩不得互相进入画像，不能确认归属的历史成绩单独提示。 |
| FR-13 | **候选人转为员工**：授权 HR 发起转员工，手机号作为账号，分配员工角色，回写解析简历与已有画像的账号关联；初始密码仅在创建响应展示一次。 | 部分实现。当前是建号和关联，不是招聘录用审批；重复转员工及账号占用有业务拦截，正式投用前仍需确认安全发放和首次改密策略。 | 无有效手机号时不建号；重复操作不再建账号；转员工后默认只访本人培训数据，不可访问招聘模块。 |
| FR-14 | **培养计划和课程**：HR 维护课程，按岗位能力基线比较现有画像，诊断差距并生成阶段计划、课程和学习任务。 | 已实现。当前同一候选人和岗位重新生成计划会作废旧计划；无适配资源时不应假装已找到课程。 | 展示能力现值、目标和差距；重新生成后的可执行计划清楚；本人和其他员工的计划不混淆。 |
| FR-15 | **学习过程、课后考核和成长台账**：员工查看本人任务、上报进度并完成课程；HR 可关联考核提交；符合条件的考核通过时更新画像并写入成长台账。 | 部分实现。现行进度和学时依赖客户端上报，并非完整的可信学时校验；课后考核仍用姓名校验提交人与计划对象，需和 FR-12 一并改为显式身份关联。 | 未达进度或学时不得手动完成；提交不归属本人或课程时应拒绝（目标态）；同一有效考核重复提交不应重复加分或写台账。 |

### 4.4 系统管理与运行

| ID | 需求 | 状态与现行边界 | 验收口径 |
|---|---|---|---|
| FR-16 | **登录、会话、菜单和访问拒绝**：校验账号状态，应用角色权限，按角色进入相应页面，并支持退出。 | 已实现。后端使用 JWT；Redis 可缺失，缺失时不可将退出等同于服务端撤销所有旧令牌。 | 未登录访问受保护接口返回 401；无权限返回 403；员工默认进入培训；Redis 可用与不可用两种会话场景分别测试。 |
| FR-17 | **系统查询和操作审计**：权限范围内查看用户、角色和操作记录；写接口记录操作者、动作、路径、状态和耗时等。 | 部分实现。通用审计日志不是不可变业务决策记录；当前未承诺完整的后台用户/角色管理、敏感查阅审计或对象级审计。 | 普通员工与未授权 HR 不应查询系统日志；一次授权写操作可对应到操作记录；日志不包含密码、访问令牌和简历原文。 |
| FR-18 | **依赖状态与降级**：有明确的服务健康状态；MySQL 作为业务数据来源，存储保留原件，Redis 和 AI/嵌入/向量服务各有明确依赖和故障表现。 | 部分实现。已有健康、AI 和向量状态接口；各依赖失败时的端到端状态、恢复时限和告警尚未统一验证。 | AI 失败时能区分规则降级与解析失败；向量功能不可用不阻断核心规则匹配；核心数据库不可用不报整体健康。 |

## 5. 数据对象与跨模块规则

| 对象 | 当前定位 | 需要保护的关系 |
|---|---|---|
| `resume_files` / `parse_tasks` / `parse_logs` | 文件元数据、解析任务和日志 | 原始文件是核验依据；任务与文件、日志、提取结果必须能串联。 |
| `parsed_resumes` | 提取和人工校对后的简历版本，也是当前若干业务关系的临时主键 | 一个上传文件与对应解析结果区分标识；现行/历史版本不能与用户账号混淆。 |
| `candidates` | 已建模，尚非现行招聘链路的一致主档 | 不能把现有业务里的 `candidate_id` 一律理解为 `candidates.id`；画像、计划等多个字段目前存的是 `parsed_resumes.id`。 |
| `job_profiles` / `match_results` / `match_lists` | 岗位规则与当前匹配结果/名单 | 分数、阈值、状态、原因需要对应同次计算；下一阶段正式历史需按批次而非岗位直接覆盖。 |
| `exam_assignments` / `exam_submissions` | 测评绑定和提交成绩 | 优先用明确的绑定关联人、卷和成绩；姓名只能展示，不能作为自动关联依据。 |
| `talent_profiles` / `prejob_plans` / `prejob_plan_tasks` / `growth_ledger` | 分别记录能力画像、培养计划、学习任务与可追溯变化 | 能力变化应有明确来源；同一有效证据不重复计算；更换简历版本不能改变证据的人员归属。 |
| `sys_users` / `sys_roles` / `sys_operation_logs` | 登录账号、角色和系统操作 | 员工账号不是简历记录，登录权限不是候选人身份，系统操作日志不是业务状态机。 |

**数据来源原则：**结构化事实、原件及权限关联以 MySQL 和受控文件存储为准；向量索引只服务召回，允许重建；模型生成内容应标注来源或降级，不应无依据填补关键事实；匹配规则应与岗位能力证据对应，不因仅修改联系方式等无关字段而改变能力评价（目标态）。

## 6. 非功能需求与度量

| ID | 要求 | 验收与度量 |
|---|---|---|
| NFR-01 | **授权与数据隔离**：按动作和具体对象判断访问；敏感字段最小展示。 | 按管理员、两部门 HR、两员工建立角色 × 接口 × 对象测试，覆盖列表、详情、汇总、附件、测评、画像和计划；授权判断由后端执行。画像读接口、工作台部分汇总与审计列表应优先核对数据范围。 |
| NFR-02 | **可解释、可复现**：评分输出需标明硬条件、分项、数据来源、规则版本与缺失证据。 | 给定同一输入和规则重算应一致；下一阶段复盘不能读取最新规则或最新画像来解释历史分数；对照异常和边界样本。 |
| NFR-03 | **可靠处理**：重复请求不产生重复业务副作用；可重试故障与人工干预故障可区分。 | 测试重复上传/提交、并发认领、模型超时、进程中断、更新后向量过期；记录积压、重试和恢复结果。需分别定义业务幂等键，不宜使用同一个键处理所有任务。 |
| NFR-04 | **隐私与安全**：限制简历、原件、答卷和账号密码的访问与留存；避免将敏感字段送入不必要的模型调用。 | 日志不记录原文、凭据或初始密码；部署前确认数据留存和删除流程、模型发送范围、备份恢复和改密策略；演示用合成或脱敏数据。 |
| NFR-05 | **可维护、可交付**：保持 View / Controller / Service / Model 的边界；迁移与验收可重复。 | 对评分纯函数、API 契约和数据库迁移分别加测试；可以使用文档复现启动与基础验证。当前工作区未发现 Git 仓库，建议先建立版本历史和自动测试门禁。 |
| NFR-06 | **使用体验与性能**：主要页面应有加载、空数据、失败、禁止访问和可恢复操作反馈；大批量操作不挡住正常浏览。 | 分别记录解析耗时、失败率、匹配响应、人工校对量和复核耗时；按同一数据集记录 P50/P95、样本量和依赖条件。先测基线再设指标，不写未测出的性能或效率承诺。 |

## 7. 已知差距与下一阶段优先级

### 7.1 差距登记

| 编号 | 现状证据 | 影响 | 处理顺序 |
|---|---|---|---|
| G-01 | 已用合成样例实测：显式专业不符时仍以 **82 分通过**；只增加手机号和邮箱，**82 → 85 分**。 | 配置与执行不一致，联系方式影响评分，现有 36 条离线断言没有覆盖这些场景。 | P0 |
| G-02 | 代码显示画像按 `candidate_name` 查询提交，课后考核也以姓名比对。 | 同名串入证据，影响画像、匹配和培训结果。当前为静态发现，未用真实个人数据验证。 | P0 |
| G-03 | 匹配服务重跑时按岗位删除并重写两张结果表；当前没有独立 HR 决定记录。 | 规则或简历变化后，无法据现有结果完整复盘原决策。 | P1 |
| G-04 | 详情与列表的授权查询不统一，工作台部分汇总查询未使用同一数据范围。 | 权限风险。需要隔离环境逐接口确认，而不是仅依据菜单权限认定安全。 | P0 核查 |
| G-05 | 解析由页面请求推进，向量过期判定主要基于条数。 | 离开页面、worker 中断或简历原地修订时，处理或索引一致性难以保证。 | P2 |
| G-06 | 招聘流转、转员工建号、录用审批尚未被统一流水连接；员工独立答题未实现。 | 当前有功能联动，但尚未形成正式招聘审批或员工考试产品。 | 主线稳定后决定是否扩展 |

### 7.2 下一阶段功能需求（均为规划）

| ID | 阶段 | 内容与范围控制 | 验收示例 |
|---|---|---|---|
| NEXT-01 | P0 · 规则正确性 | 建立岗位条件与运算符矩阵，统一校验与执行；定义「满足 / 不满足 / 证据缺失」；联系方式移出岗位能力分；试算、正式匹配共用规则实现。 | 不支持的条件不可发布；缺少硬条件证据进入待核验；仅补手机号不得改变能力分；覆盖等于门槛、低于门槛、缺失值。 |
| NEXT-02 | P0 · 证据归属与授权 | 先用现有测评绑定和简历关联修正画像及课后考核；修补核实的对象级授权缺口。稳定候选人 ID 的回填、冲突复核和版本迁移单独设计，不一次改全库。 | 同名两人各有成绩时，画像只得到自己的；未绑定旧成绩不自动计入；相同角色的不同部门只能访问被允许的对象。 |
| NEXT-03 | P1 · 规则版本和匹配批次 | 保留已发布岗位规则版本；每次正式匹配产生独立批次，记录规则、评分版本、简历版本、使用的能力证据与结果快照。旧批次只读，新批次不覆盖。 | 某岗位两次匹配后都可查询；改规则和更新简历后，旧批次的分数、原因与输入证据保持不变。 |
| NEXT-04 | P1 · 人工复核 | 对候选人与岗位建立可追踪的复核记录，首期仅支持「待复核 → 入围 / 暂缓 / 不通过」。记录 HR、时间、理由和关联批次，禁止无声覆盖并发修改。 | 两名 HR 同时操作时，不会出现最后一次提交无提示覆盖；新匹配不自动改变已有人工决定；人工决定与模型建议分开。 |
| NEXT-05 | P2 · 可恢复执行与索引同步 | 沿用解析任务表，增加独立 worker、超时回收、有限重试和失败分类；索引按内容版本更新。先不扩展为多服务或引入额外消息中间件。 | 关闭浏览器、模拟网关超时或中途终止 worker 后任务仍能推进；重复认领不重复落库；修改技能即使不改变总条数也触发更新。 |

**推荐首个交付切片：**依次做 NEXT-01、NEXT-02，再把 NEXT-03 和 NEXT-04 合成一条演示主线。演示应使用可公开的样本，证明「同名不串分、规则变更后旧结论可查、多人复核不覆盖」。NEXT-05 作为可靠性增强，在主线口径稳定后推进。

### 建议记录的项目成果

- **规则正确性**：保留数据集版本、每项规则的正反例、评分差异原因，不只展示一个总准确率。
- **业务价值**：用相同脱敏样本比较人工修正次数、单份复核耗时和剩余待核验数量；没有人评前后对照，不宣称节省多少人时。
- **工程能力**：展示一张身份与匹配数据关系图、一张复核状态图、能复跑的测试，以及能演示的并发或失败恢复案例。

## 9. 待确认的产品口径

这些是下一阶段设计输入，不阻塞对现状的阅读：

1. **硬条件允许哪些字段？** 专业、城市等是否真的要做硬门槛，还是仅用于提示？缺失证据能否推进到人工复核？建议默认待核验，不自动淘汰。
2. **谁有复核权？** 默认由岗位负责 HR 决策；部门负责人是否需要二审、谁能重开结论、是否必须填写理由，需要确认。
3. **测评谁来答？** 候选人是否需要受控自助链接，员工是否需要自助课后考核；若纳入，需另定身份核验、截止、重考和权限口径。
4. **录用是否进入首期复核链？** 当前实现仅提供转员工建号。建议先做可审计的入围与筛选复核，录用审批、Offer 和转员工前置校验另期决定。
5. **文件和历史证据保留多久？** 正式投用前需确认原件、测评、审计、备份和向量数据的保留与删除范围，以及模型可接触的字段。
